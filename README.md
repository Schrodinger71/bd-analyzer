# bd-analyzer

Программное средство анализа защищенности конфигураций PostgreSQL по формализованным контрольным профилям, построенным по мотивам статьи о проверке соответствия требованиям приказа ФСТЭК России N 64.

Проект включает:

- модуль сбора конфигурации из `postgresql.conf`, `pg_hba.conf`, `pg_ident.conf`;
- модуль нормализации параметров в единую внутреннюю модель;
- модуль анализа с набором правил по аутентификации, доступу, аудиту, резервированию и контролю целостности;
- модуль отчетности с экспортом в `TXT`, `HTML`, `JSON` и `PDF`;
- графический интерфейс на Fyne и CLI для пакетного запуска.

## Быстрый запуск CLI

```powershell
go run .\cmd\app-cli\main.go `
  -target "Контур-1" `
  -class 4 `
  -conf ".\examples\demo\postgresql.conf" `
  -meta ".\examples\demo\metadata.json" `
  -format html `
  -out ".\report.html"
```

Если `-out` не указан, отчет печатается в консоль.

## Metadata JSON

Часть проверок в статье опирается не только на конфигурационные файлы, но и на сведения о ролях, резервном копировании, аудите и механизмах контроля целостности. Для этого проект поддерживает дополнительный `metadata JSON`.

Пример структуры:

```json
{
  "settings": {
    "password_min_length": "12",
    "auth_max_failed_attempts": "5",
    "password_encryption": "scram-sha-256"
  },
  "audit": {
    "enabled": true,
    "provider": "pgaudit",
    "events": ["ddl", "role", "write"],
    "log_directory_protected": true,
    "immutable_storage": false
  },
  "backup": {
    "enabled": true,
    "schedule": "daily",
    "retention_days": 14,
    "encrypted": true,
    "tested_restore": true
  },
  "integrity": {
    "config_control_enabled": true,
    "checksums_enabled": true
  },
  "roles": [
    {
      "name": "postgres",
      "login": true,
      "superuser": true,

    }
  ]
}
```

## Демонстрационный набор

В каталоге `examples/demo` лежит готовый комплект файлов:

- `postgresql.conf`
- `pg_hba.conf`
- `pg_ident.conf`
- `metadata.json` — частично заполненный демо-профиль (намеренно не проходит все проверки)
- `metadata-class1.json` — эталонный профиль для **1 класса защиты** (максимальный профиль контроля), проходит все 16 контрольных правил со счетом 100/100 (см. ниже)

Проверка демо-профиля:

```powershell
go run .\cmd\app-cli\main.go -target demo -class 4 -conf .\examples\demo\postgresql.conf -meta .\examples\demo\metadata.json -format txt
```

### metadata JSON — отдельный файл, не привязанный к источнику конфигурации

`metadata JSON` (поле `-meta` в CLI и одноименное поле в GUI) — это **всегда отдельный файл**, независимо от того, как собирается остальная конфигурация:

- при анализе только локальных `.conf`-файлов — дополняет их;
- при анализе **живой** PostgreSQL (host/port/login) — подключается одновременно с live-подключением и дополняет то, что приложение не может получить через SQL-интроспекцию (сертификация СУБД/ОС, состав ролей администрирования, аудит, резервное копирование, отказоустойчивость, безопасное удаление и т.д.);
- сведения из metadata JSON имеют приоритет: если один и тот же параметр получен и из live-БД/conf-файла, и из metadata JSON, побеждает значение из metadata JSON (`internal/collector/collector.go`, `Collect()`).

Эталонный пример максимального профиля (1 класс защиты) — `examples/demo/metadata-class1.json`. Он специально составлен так, чтобы пройти **все** правила из `internal/analyzer/rules64.go` без живого подключения и без conf-файлов (сам по себе является достаточным источником данных). Проверить:

```powershell
go run .\cmd\app-cli\main.go -target "Эталон-1класс" -class 1 -meta .\examples\demo\metadata-class1.json -port 0 -format txt
```

(`-port 0` нужен только из-за особенности CLI: флаг `-port` по умолчанию равен `5432`, из-за чего `UsesLiveConnection()` считает запрос live-запросом даже без `-host`/`-user`; в GUI это не требуется — переключатель «живая PostgreSQL» там явный.)

Используйте `metadata-class1.json` как образец структуры: скопируйте файл и замените значения на фактические сведения о вашем объекте информатизации — большинство ключей в `settings` соответствуют конкретной проверке в `rules64.go` и снабжены комментарием в самом файле (`notes`).

## Автоматическое усиление защищенности (модуль remediation)

После анализа модуль `internal/remediation` строит план усиления по каждому несоответствию ФСТЭК №64. Часть пунктов плана помечена как `AutoApply: true` — это безопасные, обратимые изменения, которые можно применить к **живой** PostgreSQL прямо из GUI (вкладка «Усиление» → «Применить безопасные изменения») одним подтверждением. Каждое автоприменение выполняется в отдельном соединении (`internal/remediation/remediation.go`, `ApplySafeWithProgress`), после применения автоматически выполняется `SHOW <параметр>` для проверки и повторный запуск анализа, чтобы сразу показать новый балл.

Критерий отбора в автоприменение: изменение не должно требовать перезапуска службы PostgreSQL, не должно затрагивать существующие роли/гранты и не должно иметь риска разрыва соединений или блокировки доступа администратора.

### Что применяется автоматически

| Находка ФСТЭК | Что делает | SQL | Зачем |
|---|---|---|---|
| `AUTH-002` (защищенное хранение паролей) | Переводит хранение новых паролей на SCRAM | `ALTER SYSTEM SET password_encryption = 'scram-sha-256'` | Требование п.8.1 приказа №64 — пароли не должны храниться в виде, уязвимом к компрометации (MD5). Действующие пароли не перевыпускаются автоматически — это нужно сделать вручную для критичных учетных записей. |
| `AUTH-002` (жизненный цикл сессий) | Ограничивает зависшие, простаивающие и «мертвые» сессии | `ALTER SYSTEM SET idle_in_transaction_session_timeout = '15min'`<br>`ALTER SYSTEM SET lock_timeout = '30s'`<br>`ALTER SYSTEM SET tcp_keepalives_idle = '300'`<br>`ALTER SYSTEM SET tcp_keepalives_interval = '30'`<br>`ALTER SYSTEM SET tcp_keepalives_count = '3'` | Снижает риск удержания аутентифицированной сессии или блокировки ресурса дольше необходимого. Пороги намеренно щадящие, чтобы не задеть штатную нагрузку. `statement_timeout` сюда **намеренно не включен** — см. раздел «Что НЕ применяется автоматически». |
| `ACCESS-002` (ролевая модель) | Запрещает роли PUBLIC создавать объекты в схеме `public` и новые схемы в подключенной базе | `REVOKE CREATE ON SCHEMA public FROM PUBLIC`<br>`REVOKE CREATE ON DATABASE "<db>" FROM PUBLIC` (если известно имя живой БД) | Закрывает стандартный вектор повышения привилегий через схему `public`, открытую «по умолчанию» в PostgreSQL. Право `CONNECT` не затрагивается — действующие подключения не ломаются. |
| `ACCESS-003` (матрицы доступа) | Меняет права по умолчанию для **будущих** объектов схемы `public` | `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM PUBLIC`<br>`... ON FUNCTIONS FROM PUBLIC`<br>`... ON SEQUENCES FROM PUBLIC` | Закрывает blanket-доступ PUBLIC к новым таблицам/функциям/последовательностям. Уже существующие объекты и их права **не трогает** — точечная ревизия текущих грантов остается ручным шагом плана. |
| `AUD-001`, `AUD-002` (регистрация событий) | Включает безопасный базовый аудит PostgreSQL | `ALTER SYSTEM SET log_connections = 'on'`<br>`log_disconnections = 'on'`<br>`log_min_error_statement = 'error'`<br>`log_line_prefix = '%m [%p] db=%d,user=%u,app=%a,client=%h '`<br>`log_error_verbosity = 'verbose'`<br>`log_file_mode = '0600'`<br>`log_rotation_age = '1d'`<br>`log_rotation_size = '100MB'`<br>`log_statement = 'ddl'` | Покрывает обязательную регистрацию подключений/отключений/ошибок, ограничивает доступ к файлу журнала, включает ротацию и логирует DDL/ролевые события (CREATE/ALTER/DROP, управление ролями). `log_statement` намеренно ограничен `'ddl'`, а не `'mod'` — см. ниже. |

После каждого `ALTER SYSTEM SET ...` автоматически выполняется `SELECT pg_reload_conf()`, изменения вступают в силу без перезапуска службы. После `REVOKE`/`ALTER DEFAULT PRIVILEGES` перезагрузка конфигурации не требуется — права применяются сразу.

### Что НЕ применяется автоматически — и почему

Это осознанные границы, а не недоработка:

- **Изменение атрибутов ролей** (`ALTER ROLE ... NOSUPERUSER/NOBYPASSRLS/NOREPLICATION`, сокращение числа SUPERUSER-ролей). Ошибка в выборе роли может заблокировать доступ администратора без чистого отката — остается в ручном плане («Пересобрать ролевую модель»).
- **Подключение pgAudit через `shared_preload_libraries`**. `ALTER SYSTEM SET shared_preload_libraries = ...` полностью перезаписывает значение и может «выбить» уже загруженные расширения (`pg_stat_statements`, `timescaledb` и т.п.), а само изменение требует **перезапуска** службы PostgreSQL — то есть простоя, который инструмент не вправе инициировать самостоятельно.
- **`statement_timeout`**. В отличие от `lock_timeout`, общий лимит длительности запроса риск-зависим от нагрузки: может оборвать легитимный долгий `pg_dump`, построение индекса или миграцию. Безопасного универсального значения нет — решение оставлено за администратором.
- **`log_statement = 'mod'` или `log_min_duration_statement`**. Логирование текста DML-операторов или долгих запросов может записать в журнал чувствительные данные (пароли, ПДн) прямо в тексте SQL — это противоречит требованиям защиты информации, поэтому глубина аудита по умолчанию ограничена `'ddl'`.
- **Существующие гранты `EXECUTE`/`SELECT` на уже созданные объекты** (`ACCESS-003`). PostgreSQL по умолчанию выдает `EXECUTE` на функции роли PUBLIC — массовый отзыв у уже работающих объектов может сломать приложение, не имеющее явных грантов. Автоматизация применяется только к **default privileges** для будущих объектов.
- **Резервное копирование (`BACKUP-001`), отказоустойчивый кластер (`AVAIL-001`), безопасное удаление (`MEM-001`)**. Это архитектурные/эксплуатационные решения (расписание бэкапов, HA-схема, политика wipe), которые невозможно безопасно свести к одному SQL-вызову.
- **Атрибуты сертификации и документирования** (`TRUST-001`, `OS-001`, `PERF-001`, поля `metadata JSON` вида `os_certified`, `dbms_trust_level`). Инструмент намеренно не подставляет эти значения автоматически — это были бы сфабрикованные свидетельства соответствия, а не реальная проверка.

### Как это работает технически

- `remediation.Build(result, snapshot)` строит полный план усиления (включая ручные шаги) для каждой непройденной находки.
- `remediation.AutoApplicable(result, snapshot)` отбирает из плана только пункты с `AutoApply: true` и непустым `SQL`.
- `remediation.ApplySafeWithProgress(...)` подключается к живой PostgreSQL отдельным соединением, последовательно выполняет SQL, при необходимости вызывает `pg_reload_conf()`, затем для каждого примененного `ALTER SYSTEM SET ...` выполняет `SHOW <параметр>` для проверки фактического значения.
- GUI после применения автоматически перезапускает анализ и показывает изменение балла «было → стало».

## Важно

Текущие контрольные профили реализуют практическую интерпретацию статьи и подходят как основа для развития базы правил. Для строгого регуляторного аудита под конкретный объект информатизации правила стоит дополнить точной матрицей требований вашей организации.
